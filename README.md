# Baghewala Digital Twin

**Digital Twin for Well-to-Surface Optimization of Cyclic Steam Stimulation (CSS) and Sucker Rod Pump (SRP) Operations for Heavy Oil Wells of Baghewala Field** — browser-based MVP.

A **physics-informed digital twin with supervised automation**. Every operating change flows

```
Prediction → Recommendation → Safety gate → Auto-execute (operator may intervene) → (simulated) change → Outcome → Model trust
```

**Control modes** (switch in the scenario bar or on the Safety page):

- **AUTO (supervised, default)** — a recommendation that passes *every* safety check with no warnings and ≥ 85 % model confidence executes automatically after an 8-second intervention window. The operator can **HOLD**, **MODIFY**, **REJECT** or **EXECUTE NOW** during the window, and **ROLL BACK** afterwards from any page. Anything the gate cannot fully clear (violations, warnings, low confidence) is **escalated** to the operator and can never auto-execute.
- **ADVISORY** — every recommendation waits for explicit operator approval.

**Low-score test case (W-19).** Press **TEST CASE: LOW SCORE (W-19)** in the scenario bar. W-19 has a failed downhole temperature gauge (temperature inferred from the surface flowline), so its model confidence is ~82 % — above the 80 % safety minimum but below the 85 % automation threshold. The Causal Analysis page shows **FIELD OFFICER APPROVAL REQUIRED**; at the decision point the action is escalated instead of auto-executing, and the officer chooses **APPROVE**, **MODIFY** or **REJECT** on the Safety page. Covered by `npm run check:automation` and `node scripts/shot-testcase.mjs`.

All setpoints are simulated; nothing connects to real equipment. Every automated and operator action is written to the audit trail.

> **Data honesty.** Everything in this application is a **demonstration simulation**. Field counts (52 / 33 / 19) are shown as *field reference / demonstration*. Well values, time series, CSS cycles and model metrics are generated by the included models and are **not** Baghewala measurements, and are **not** field-validated. No official logos or credentials are used.

## Quick start

```bash
npm install
npm run dev          # http://localhost:5173
npm run build        # type-check + production build to dist/
npm run preview      # serve the production build
```

Requires Node 18+ (developed on Node 24). WebGL is needed for the 3D view; without it a static technical drawing is shown.

Optional checks:

```bash
npm run check:models   # asserts the model chain reproduces the demo story (22 checks)
npm run e2e            # headless-Chrome journey: field → W-17 → scenario → approve → outcome (needs `npm run dev` running and Chrome installed; set CHROME_PATH if not default)
```

## The demonstration (≈ 90 s)

1. Open **Field Command Center** (`/field`) — schematic map of 52 wells; hover for live values, click a marker.
2. Open **W-17** → the 3D **Well Digital Twin** (CAD-derived pumping unit, animated at the simulated SPM).
3. Press **START DEMO SCENARIO** (top bar). With *auto-follow* on, the app moves through the relevant pages:

| Phase | What happens | Page |
|---|---|---|
| 1–2 | Normal operation; CSS-08 thermal support ends | Twin / Thermal |
| 3–5 | Physics-informed thermal decline; temperature ↓, viscosity ↑ (μ = A·exp(B/T)) | Thermal |
| 6 | Cooling confirmed (≥ 6 h) → +24 h rod-load forecast rises (72 % → 84 %) | SRP |
| 7 | Predicted risk **HIGH**, forecast dynacard shows incipient pump-off | Causal |
| 8 | **AI-assisted recommendation: SPM 10 → 8** (VFD 42 → 36 Hz), confidence 91 % | Optimization |
| 9 | Safety engine re-validates independently → **ALL SAFETY CHECKS PASSED** | Safety |
| 10 | **Simulation holds — OPERATOR APPROVAL REQUIRED** (Approve / Modify / Reject) | Safety |
| 11–14 | Approved setpoint ramps; the 3D unit visibly slows; +24 h fast-forward; rod load falls | Twin / SRP |
| 15–16 | Before / after vs. no-action; predicted 76 % vs simulated observed ≈ 74 % (error ≈ 3 %) | Outcome / History |

Controls: **PAUSE / RESUME / RESET / RESTART**. *Modify* lets the operator change the proposal; every change is re-validated (try "Test unsafe: 13 SPM" — approval is blocked). *Reject* runs the no-action path (load → ~81 %, risk stays HIGH). Outside the scenario, the SPM slider on the Twin page is a what-if simulation input.

## Architecture

```
src/
  types/                 domain interfaces (Well, CSSCycle, SRPState, Prediction, Recommendation, SafetyResult …)
  services/
    modelConfig.ts       CONFIGURED parameters (crude, thermal, SRP calibration, safety limits)
    thermalModel.ts      physics baseline + ML-residual stand-in + forecast bands
    viscosityModel.ts    μ(T) = A·exp(B/T)
    srpModel.ts          rod load, torque, fillage, efficiency, production, risk/health
    dynacardModel.ts     synthetic cards + DynacardClassifier interface (rule-based today)
    recommendationEngine.ts  forecast + constraint-aware candidate search
    safetyEngine.ts      validateRecommendation(rec, wellState) → { safe, warnings, violations, confidenceStatus }
    simulationEngine.ts  composes models; "plant" (simulated observation) vs "model" (prediction)
    dataSource.ts        FieldDataSource interface; LocalDemoDataSource today
  store/twinStore.ts     zustand store: clock, scenario state machine, approval gate, outcome, audit log
  data/                  wells (52, deterministic), CSS cycles, scenario script, historical metrics
  components/            layout, field, twin (3D), operations, thermal, srp, intelligence, safety, outcome
  pages/                 one file per route (Twin page is code-split so Three.js loads lazily)
scripts/
  cad/                   SAT → GLB converter, rig rules for the supplied unit, pivot finder
  check-models.ts        model-chain assertions
  e2e.mjs, shot-*.mjs    headless-browser journey & visual checks
```

### Physics-informed model chain (demonstration calibration)

- **Thermal** (PHYSICS-INFORMED THERMAL APPROXIMATION): `T(t) = T_base + A·exp(−k·t)` after CSS support ends, `T_final = T_physics + ML_residual`. Forecast uncertainty grows with horizon (±4 °C at +24 h ≈ 95 %). Forecasts only include decline after **≥ 6 h of confirmed cooling** (avoids false alarms).
- **Viscosity**: Andrade form `μ(T) = A·exp(B/T[K])`, A = 0.2071 cP, B = 2594 K (72 °C → 380 cP, 68 °C → 415 cP).
- **SRP**: `L = L_static + L_dyn·(S·N²) + L_visc·(S·N)·(μ/μ_ref)^p`; fillage limited by viscous barrel-fill time ∝ μ^a / N with a fluid-pound efficiency penalty; production = displacement × efficiency × (1 − WC); peak torque from PPRL vs fixed counterbalance.
- **Plant vs model**: simulated observations use slightly different parameters (viscosity exponent, thermal bias) from the prediction model, so prediction error is computed honestly rather than being zero by construction.

### Safety model

The safety engine does not trust the recommendation's numbers — it re-evaluates the proposal with the SRP model at the forecast conditions, including a conservative (+1σ viscosity, P84) case. Checks: max/min SPM, max change per action, max rod load, max gearbox torque, stroke range, VFD limits, pump operating range (fillage), minimum model confidence. Any violation blocks **APPROVE**. Nothing executes without an explicit operator decision; approval only issues a *simulated* setpoint.

### 3D model pipeline

See [`public/models/README.md`](public/models/README.md). `DigitalTwinModelViewer` resolves the model source at runtime: `/models/srp-pump.glb` (+ `srp-pump.json` articulation manifest) if present, otherwise the procedural **DIGITAL TWIN PLACEHOLDER**. A shared four-bar-linkage solver (`components/twin/kinematics.ts`) drives crank → pitman → walking beam → horsehead → polished rod → rod string → plunger at the simulated SPM, so replacing the model needs no code changes. The supplied CAD (`H20E-003-00-0.sat`) has been converted and is in place.

**Site environment** (`components/twin/environment/`): physical sky and sun with soft shadows, image-based lighting from a self-hosted CC0 HDRI (`public/env/goegap_1k.hdr`, Poly Haven), procedural Thar-style dune terrain that flattens into a fenced gravel well pad, site cabin, MCC/VFD panel, power line, flowline on pipe supports, floodlight mast, windsock, signboard, other producing wells animating in the distance, a tank farm, access road, scrub, khejri trees and rocks. Textures are generated procedurally (no downloads beyond the HDRI). The toolbar's **REALISTIC / PERFORMANCE** toggle switches ambient occlusion + SMAA post-processing on or off (remembered per browser). In downhole views the surface scenery is hidden so the cutaway stays clear.

3D state reactions: SPM drives stroke rate; polished rod / rod string colour by load (pulsing when forecast ≥ 80 %); status beacon by risk; downhole pump highlights on pump-off/low fillage; reservoir colour and heated-zone radius follow temperature.

## Future integration points (not implemented — boundaries only)

| MVP | Replace with | Boundary |
|---|---|---|
| Local demo data | SCADA / historian (OPC-UA gateway), TimescaleDB / InfluxDB | `FieldDataSource` in `services/dataSource.ts` |
| Simulated clock & plant | Real-time telemetry stream | `computeTwin` inputs / `twinStore.tick` |
| Thermal approximation + residual stand-in | Physics + trained ML residual service | `thermalModel.forecastTemperature` signature |
| Rule-based dynacard | CNN / LSTM classifier | `DynacardClassifier` (`setDynacardClassifier`) |
| Grid-search optimiser | Bayesian optimisation | `CandidateEvaluation` contract in `recommendationEngine` |
| Simulated setpoint | Operator-issued VFD setpoint via control system (still behind safety + approval) | `approve()` in `twinStore` |

Out of scope by design: authentication, backend, real SCADA/VFD control, reservoir simulation, PINN, reinforcement learning.
